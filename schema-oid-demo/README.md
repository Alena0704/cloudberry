# Подмена имени схемы

Пустое расширение создаёт только схему с обычным динамическим OID.
Сценарий моделирует небезопасную проверку через `name_check`: настоящего
выдающего привилегии кода в расширении нет.

Установить два файла расширения в каталог выбранной сборки PostgreSQL/Cloudberry:

```sh
cp empty_schema_demo.control empty_schema_demo--1.0.sql "$(pg_config --sharedir)/extension/"
psql -X -p 6000 -d postgres -f demo.sql
```

Запускать из этой директории суперпользователем в тестовой базе. В распределённой
установке файлы расширения должны быть доступны на требуемых узлах.
Имена `empty_schema_demo`, `demo_ext_schema`, `zzz` и `schema_demo_attacker` должны быть свободны.
Все изменения базы выполняются в транзакции с `ROLLBACK`.

1. Администратор создаёт расширение. Проверки имени и членства схемы в расширении дают `t`.
2. Администратор выполняет `ALTER SCHEMA demo_ext_schema RENAME TO zzz`;
   имя схемы освобождается, расширение остаётся установленным.
3. Пользователь с `CREATE` на базу создаёт свою одноимённую схему.
4. Проверка имени всё ещё даёт `t`, проверки исходного OID и членства — `f`.
   Для настоящей схемы `zzz` наоборот: имя не совпадает, но исходный OID
   и принадлежность расширению сохраняются.
5. В поддельной схеме пользователь создаёт `user_data` со своей строкой данных.
   После `RESET ROLE` суперпользовательский код доверяет имени схемы,
   читает эту таблицу через `SELECT` и удаляет её через `DROP TABLE`.
   Проверка `user_table_was_dropped` возвращает `t`.

Последние команды моделируют ошибку привилегированного обслуживающего кода,
а не обход стандартных SQL-прав: суперпользователь и так может читать и удалять
пользовательские таблицы. Ошибка в том, что он принимает пользовательский объект
за доверенный по одному лишь имени схемы. Само пустое расширение таблицы не удаляет.

Переименование выполняет администратор; обычному пользователю не приписываются
права на чужую схему. Владельцу для переименования также требуется `CREATE` на базу.
Пока имя исходной схемы занято, создать другую схему с тем же именем нельзя.
Здесь `original_oid` сохранён только для демонстрации, это не фиксированный OID
и не рекомендация хранить динамический OID в константе.

Предыдущий вариант, где администратор освобождает имя через `DROP EXTENSION`,
сохранён отдельно и тоже заканчивается откатом:

```sh
psql -X -p 6000 -d postgres -f demo-drop.sql
```

Динамический OID сам по себе безопасен. Уязвимость возникает, когда совпадение
имени считается достаточным основанием для особых прав. Проверка членства
в расширении демонстрирует различие объектов; полноценная проверка доверия
также зависит от того, кто может устанавливать расширение, владельца схемы
и прав `CREATE` на неё.
